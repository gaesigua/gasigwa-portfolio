# 5. Relocatable and Executable Object Files

## Introduction

A program does not become executable immediately after writing source code. It passes through stages — compilation, assembly, linking — producing different file types along the way. The two most important intermediate forms are:

1. **Relocatable Object Files** — produced by the assembler, cannot be executed yet
2. **Executable Object Files** — produced by the linker, ready to run

---

## 5.1 Relocatable Object Files

### Definition

A relocatable object file is an **intermediate file generated by the assembler**. It contains machine instructions and data, but memory addresses are **not yet final**. It is designed to be combined with other object files by the linker.

<div class="cp-definition">

### Key Characteristics

| Property | Detail |
|----------|--------|
| **Produced by** | The assembler (`as`) |
| **Address type** | Symbolic / relative (not absolute) |
| **Executable?** | No — cannot be run directly |
| **File extension** | `.o` (Linux/UNIX), `.obj` (Windows) |
| **Purpose** | Intermediate step before linking |

</div>

### Contents of a Relocatable Object File

| Section | Contents |
|---------|---------|
| `.text` | Machine instructions (compiled code) |
| `.data` | Initialized global/static variables |
| `.bss` | Uninitialized global/static variables |
| Symbol table | Names and types of functions/variables |
| Relocation table | Locations that need final address assignment |

### Why Relocatable Files Are Needed

- Support **modular programming** — split large programs into files
- Enable **separate compilation** — only recompile changed files
- Improve **maintenance and reuse**

---

## 5.2 Executable Object Files

### Definition

An executable object file is produced by the **linker** after combining relocatable object files and libraries. It contains **final absolute memory addresses** and can be directly loaded and executed.

<div class="cp-definition">

### Key Characteristics

| Property | Detail |
|----------|--------|
| **Produced by** | The linker (`ld`) |
| **Address type** | Absolute (final) |
| **Executable?** | Yes — loaded and run by the OS |
| **Common formats** | ELF (Linux), PE (Windows), Mach-O (macOS) |
| **Purpose** | Ready for execution |

</div>

### Contents of an Executable Object File

- Final machine code
- Initialized data
- Program entry point (`main`)
- Information for the OS loader

---

## 5.3 Relocatable vs Executable: Side-by-Side

| Feature | Relocatable Object File | Executable Object File |
|---------|------------------------|----------------------|
| **Produced by** | Assembler | Linker |
| **Address type** | Symbolic/relative | Absolute |
| **Can execute?** | No | Yes |
| **Extension** | `.o` | `.out`, `.exe`, no extension |
| **External symbols?** | May be unresolved | All resolved |
| **Purpose** | Linking input | Program execution |

---

## Programming Examples

### Example 1: Creating a Relocatable Object File

```c
/* hello.c */
#include <stdio.h>
void greet() {
    printf("Hello, World!\n");
}
```

```bash
# Compile without linking — produces relocatable object file
gcc -c hello.c       # produces hello.o

# hello.o:
# - Contains machine code for greet()
# - 'printf' reference is UNRESOLVED (U) — linker must fix this
# - Cannot be executed directly
```

---

### Example 2: Inspecting a Relocatable Object File with nm

```bash
gcc -c hello.c
nm hello.o
```

**Sample output:**
```
00000000 T greet       ← greet() is defined in this file (T = text section)
         U printf      ← printf is undefined (U) — linker will resolve it
```

- `T` = defined in text section (your code)
- `U` = undefined (will be found in another file / library)

---

### Example 3: Linking Multiple Relocatable Files to Produce an Executable

```c
/* main.c */
void greet();
int main() {
    greet();
    return 0;
}

/* greet.c */
#include <stdio.h>
void greet() {
    printf("Welcome!\n");
}
```

```bash
# Step 1: Produce two relocatable object files
gcc -c main.c         # main.o — 'greet' is U (unresolved)
gcc -c greet.c        # greet.o — 'greet' is T (defined here)

# Step 2: Link → produces executable object file
gcc main.o greet.o -o program

# Linker:
# - Finds that 'greet' in main.o matches definition in greet.o
# - Assigns final absolute addresses
# - Produces 'program' (executable)
```

---

### Example 4: Running an Executable Object File

```bash
./program          # Output: Welcome!
```

**What the OS loader does:**
1. Reads the executable format (ELF)
2. Allocates memory segments
3. Copies code and data from disk to RAM
4. Jumps to the entry point (`_start` → `main()`)

---

### Example 5: Inspecting ELF Headers with readelf

```bash
gcc hello.c -o hello
readelf -h hello
```

**Sample output:**
```
ELF Header:
  Magic:   7f 45 4c 46 ...
  Class:   ELF64
  Type:    EXEC (Executable file)
  Machine: Advanced Micro Devices X86-64
  Entry point address: 0x401060
```

This shows:
- It's a 64-bit ELF executable
- Entry point where execution begins
- Architecture (x86-64)

## Practice Problems

<details>
<summary>🧩 Practice 1 — Which Type?</summary>

**Question:** For each item, identify whether it is a relocatable object file or an executable object file:

1. `hello.o` (produced by `gcc -c hello.c`)
2. `./a.out` (produced by `gcc hello.c`)
3. `/usr/bin/ls` (Linux list command)
4. `math.o` (produced by assembling `math.s`)

**Answers:**
1. **Relocatable** — produced by `-c` flag without linking
2. **Executable** — produced by a full compilation+link
3. **Executable** — a runnable program
4. **Relocatable** — object file, output of assembler

</details>

<details>
<summary>🧩 Practice 2 — nm Output Analysis</summary>

**Question:** You run `nm program.o` and see:

```
00000000 T main
         U printf
         U malloc
0000002c T helperFn
00000000 B globalCounter
```

Interpret each entry.

**Answer:**
| Symbol | Type | Meaning |
|--------|------|---------|
| `main` | T | Defined in this file's text (.code) section |
| `printf` | U | Undefined — will be resolved from libc by linker |
| `malloc` | U | Undefined — will be resolved from libc by linker |
| `helperFn` | T | Defined in this file's code section at offset 0x2c |
| `globalCounter` | B | Defined in BSS (uninitialized data) section |

</details>

<details>
<summary>🧩 Practice 3 — Separate Compilation Benefit</summary>

**Question:** A project has 100 source files. A developer changes only `logger.c`. With separate compilation, how many files need to be recompiled? What are the steps?

**Answer:**

Only **1 file** needs to be recompiled — `logger.c`.

Steps:
```bash
# Only recompile the changed file
gcc -c logger.c         # produces new logger.o

# Re-link all 100 object files with the new logger.o
gcc main.o module1.o ... logger.o ... module99.o -o program
```

Without separate compilation (no .o files), all 100 files would need to be recompiled every time any file changes — extremely slow for large projects. Build tools like `make` automate tracking which files have changed.

</details>
